## Summary

| Item                   | Value                                          |
| ---------------------- | ---------------------------------------------- |
| **Overall risk level** | **MEDIUM**                                     |
| **Recommendation**     | **ship_with_monitoring**                       |
| **Confidence**         | **82 / 100**                                   |
| Failure modes          | 18 (0 Critical, 1 High, 13 Medium, 4 Low)      |
| Attack scenarios       | 10 (none exploitable beyond Low-Medium impact) |
| Blind spots            | 12 across all 10 categories                    |
| Blocking items         | **None**                                       |

**Why not higher risk.** The change is additive: one new table, new routes, and nothing that alters behaviour for users with `isExperimentalFeatures` off. The feature only produces a recommendation list; it never places trades, so a wrong plan costs a user's attention, not money, unless they import and act on it without reading. Authorisation is sound where it matters: every query is scoped by `userId`, foreign ids return 404, every route is guarded, and impersonation writes are blocked globally. The money maths use `big.js` and the calculator has invariant tests. I found no injection, IDOR or exfiltration path that works.

**Why not lower risk.** Five things keep this at MEDIUM:

1. The P0 UI has never been run in a browser, and there are no client unit tests (BS-003, FM-016).
2. A holding that is not in the model gets a 0% target and is sold in full, with sells on by default, no warning, no tax awareness and no "not advice" text anywhere in the UI (FM-001). This is the most likely way for a user to be materially surprised.
3. The "portfolio is already within its targets" message can still appear when nothing was within targets (FM-002). This is the same defect family as the already-fixed BUG-001, through a path the fix did not cover.
4. A missing exchange rate silently converts a foreign-currency price 1:1 for target symbols the user does not yet hold (FM-003).
5. The only rate limit on the most expensive endpoint is off by default, and there is no per-user cap on stored models (FM-015, ATK-004).

None of these corrupts data, leaks data or breaks existing features, and each has a cheap mitigation. That is a "ship, with the conditions below and a watch period", not a "fix first".

**Known open items, re-weighed.** SEC-003 (opt-in rate limiting) is real but bounded to an authenticated user who has opted into an experimental flag (Medium, FM-015). SEC-005 (full-width CSV characters) is Low and does not matter in practice because the symbol is not user-controlled text (ATK-001). English-only server messages are a Low user-experience issue (BS-007). The 2 s measurement scope is the weakest of the known items, because the real cost sits in `getDetails` plus quote fetching, which was never timed (FM-008, BS-001). The unverified UI is the item most worth closing before real users get the flag.

## Rollback Plan

The change is additive, so rollback is simple, and the one irreversible element is data left in a new table.

| Field                       | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Rollback trigger**        | Any of: sustained 5xx on `/rebalancing/*` above 2% for 15 minutes; any evidence that one user could read or change another user's model; a report of wrong trade quantities from a user (FM-003, FM-002) that cannot be fixed by turning the user's flag off; CPU or data-provider quota exhaustion attributed to `POST /rebalancing/plan`; any new 500/403 on non-rebalancing routes after deploy (permission-list change).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Rollback steps**          | 1. **Fast mitigation without a deploy** (minutes, for individual users): have the affected users turn off `isExperimentalFeatures`; the four permissions are removed on the next request and the tab disappears. There is no global server-side kill switch, so this does not stop an abusive client. 2. **Throttle** (minutes): set `ENABLE_FEATURE_RATE_LIMITING=true` and restart, if load is the concern. 3. **Code rollback**: redeploy the previous API and client images/build (reverts the permission change, `app.module.ts` registration and routes). 4. **Database**: do nothing by default. The `TargetAllocationModel` table is unreferenced by older code and harmless; the old Prisma client ignores it, and `prisma migrate deploy` on the old build does not fail on an extra applied migration. 5. **Only if the table must go** (for example a privacy request or a clean revert): add a new forward migration that runs `DROP TABLE "TargetAllocationModel";`, or run that statement manually and record it; this permanently deletes user models. Do not edit or delete the applied migration folder or the `_prisma_migrations` row on a shared database. |
| **Estimated recovery time** | Flag-off per user: under 5 minutes. Rate limit on: about 5 minutes (restart). Full code rollback: 15-30 minutes (build/redeploy pipeline). Table drop: under 5 minutes of execution, but only after the code rollback is live.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Rollback owner**          | The release engineer / backend on-call for the deploy, with the feature owner (KBSHari) for diagnosis.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Rollback risk**           | Low. The table and any saved models persist across a code rollback; a later redeploy brings them back and they are revalidated (BS-012). A rollback that drops the table loses all user models irreversibly (acceptable only if the product confirms the data is disposable, as the design review's MISS-002 assumed). Rolling back only the client or only the API leaves a client calling missing routes (404 and the generic error message) or an API with no UI; roll back together. If an unrelated migration is released after this one, do not drop the table in a way that breaks the ordering.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## Sign-Off

- **Recommendation:** `ship_with_monitoring`
- **Overall risk level:** MEDIUM
- **Confidence score:** 82 / 100 (all required artifacts and all core implementation files were read; deducted for no browser run, no database or load run, no `client-notes/risk.md`, and the client templates being sampled rather than line-by-line reviewed).
- **Blocking issues:** none.

**Justification.** A `fix_first` verdict needs a finding that makes the feature unsafe to release even behind its flag: data loss, a security hole, a breakage of existing behaviour, or a failure that cannot be contained. None qualifies. The highest-severity items (FM-001, a sell-everything-outside-the-model default with no warning; FM-002, a misleading message) cause a confusing or unwelcome recommendation, not an unauthorised action, and a user must act on them by hand. The feature is off by default for everyone, additive in the database, and trivially disabled per user. A `redesign` verdict is not warranted: the architecture (pure calculator, scoped service, guarded controllers) held up under inspection and the issues are local fixes of hours, not days.

**Conditions for the verdict:** complete R-001 to R-004 before the PR is merged or the flag is offered to any real user (a smoke test, the all-clear message fix, the unmodelled-sell warning with a disclaimer, and a clean commit), and treat R-005 to R-009 as first-sprint work. If R-001 finds a runtime defect in the UI, escalate that single defect to `fix_first`.
