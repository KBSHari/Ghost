## Summary

The design is sound in structure: it reuses the existing NestJS and Angular patterns, isolates the calculation in a pure core, adds one additive table, and introduces no new dependency. Mode B checking confirmed most of the claims about existing code, but found **one factual error about cash handling, two missing design details that would fail at implementation (symbol resolution in the validator, and nested DTO validation under the global whitelist pipe), and one gap in rate limiting.** None is critical, since each can be fixed without changing the architecture.

| ARCH-001 | data_flow       | major    | high   | small   | false    | The design says total value V includes "cash positions in scope" among holdings. In the code, `getDetails` does not return cash as holdings (outside the emergency-fund case). If implemented as written, V would exclude cash, so every target weight and the cash reserve would be wrong.       | State explicitly: V = sum of holding values + `getCashDetails` balance for the same account filter and base currency. | ARCH-002 | coupling        | major    | high   | medium  | false    | COMP-001 is a pure validator in `libs/common`, but the hierarchy rule "symbol belongs to this sub-class and class" needs the symbol's class and sub-class, which live in `SymbolProfile`. A pure function cannot look this up, and the client has no such data when editing.                      | Make the validator take a symbol-to-(class, sub-class) lookup supplied by the caller: the server builds it from `SymbolProfileService`, the client from the existing asset-profile search results. Require every symbol node to resolve to a known profile; return a `UNKNOWN_SYMBOL` error otherwise. | Validate hierarchy only on the server and keep the client check to sums and bands (simpler, but loses instant feedback on symbol/class mismatch).           |
| ARCH-003 | maintainability | major    | high   | small   | false    | The global `ValidationPipe` uses `whitelist` and `forbidNonWhitelisted`. A `targets` tree sent as nested plain objects would have every undecorated property rejected or stripped. The design lists three DTO files but no nested node classes.                                                   | Define nested DTO classes (class node, sub-class node, symbol node, sector target, parameters) each with `class-validator` decorators, `@ValidateNested` and `@Type`, following `import-data.dto.ts`. Cap array sizes.                                                                                 | Store `targets` as an opaque JSON value validated only by COMP-001 (needs a custom validator that bypasses the pipe — non-standard here).                   |
| ARCH-004 | scalability     | major    | medium | trivial | false    | The plan endpoint is CPU- and data-heavy (`getDetails` plus quotes), and throttling is applied per controller in this codebase, not by default. A client in a loop could load the API.                                                                                                            | Apply the existing throttling to `POST /rebalancing/plan` (as AI/auth controllers do) with a per-user limit, and document the chosen value.                                                                                                                                                            | Cache the last plan per user for a short TTL (more state, rejected for now).                                                                                |
| ARCH-005 | maintainability | minor    | low    | trivial | false    | ADR-006 adds `accessRebalancing` to the ADMIN and USER lists and removes it when experimental features are off. ## Positive Aspects

- No new dependency, additive schema, and no change to any existing service signature.
- Pure, testable calculator with explicit invariants and well-chosen edge cases.
- Security thinking is concrete (IDOR via 404, CSV formula injection, log hygiene, cascade delete).
- The design noticed and used `ASSET_CLASS_MAPPING`, resolving a real ambiguity in the requirements.
- Flags F-001 to F-005 are honest and actionable.

### Conditions (implementation must address)

1. **C-1 (ARCH-001):** Obtain cash from `AccountService.getCashDetails` for the same filters and base currency; V = holdings + cash; never assume cash is in the holdings list.
2. **C-2 (ARCH-002):** The target validator takes a symbol resolver (class and sub-class per symbol); unresolved symbols are rejected.
3. **C-3 (ARCH-003):** Define nested, decorated DTO classes for the whole target tree and parameters, with size caps.
4. **C-4 (ARCH-004):** Apply per-user throttling to `POST /rebalancing/plan`.
