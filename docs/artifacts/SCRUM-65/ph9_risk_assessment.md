## Summary

- **Overall risk:** MEDIUM
- **Recommendation:** `ship_with_monitoring`
- **Failure modes:** 14 (0 critical, 0 high, 5 medium, 9 low) | **Attack scenarios:** 8 (5 not exploitable, 1 limited by the existing debounce (ATK-004), 1 partly exploitable through a compromised data provider (ATK-005), 1 exploitable only with privileged database access (ATK-006)) | **Blind spots:** all 10 categories evaluated, 2 found nothing new (BS-002, BS-006)
- **Blocking items:** 0 (three actions are required before shipping and are listed under Recommendations)

Why it is not higher: the behaviour is opt-in (`isExperimentalFeatures`), the migration is a single additive table with no foreign keys, every new read path falls back to the existing data, the one write path (the gathering job) cannot fail a job, and the new response field is withheld from restricted views. A rollback is a setting change.

Why it is not lower: the most important risk is not a crash but a quiet one. With the flag on, a holding whose exchange rate is missing is correctly left out of the totals, but only the **analysis page** says so. The client reads no error flags from the portfolio responses anywhere, so the holdings list, allocations, X-ray report, FIRE calculator, public page and MCP tools all present a reduced portfolio as if it were complete (FM-001). That is the exact class of problem this ticket exists to remove, relocated rather than eliminated, and it is the main reason monitoring is required.

## Blind Spots

| ID     | Category                 | Finding                                                                                                                                                                                                       |
| ------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BS-001 | scalability              | Snapshots refresh after a minute on access, so active users recompute often; the new path reads two tables. See FM-011.                                                                                       |
| BS-002 | edge_cases               | Time zones (FM-012), future-dated activities (adjusted to today by the existing code), derived currencies such as GBp (covered), and activities dated before any rate (excluded by design). No new gap found. |
| BS-003 | user_behavior            | A user can toggle the flag back and forth and see different history (FM-005). The notice's details are collapsed by default; a user may not open them.                                                        |
| BS-004 | third_party_dependencies | The default provider's FX coverage and rate limits are unverified (ASM-004, ASM-007). A provider change of symbol format would silently stop new rows.                                                        |
| BS-005 | data_consistency         | Two stores with a precedence rule (FM-003) and a one-way sync: deletions in `MarketData` do not reach the new table.                                                                                          |
| BS-006 | compliance               | No personal data in the new table; logs carry no amounts or identifiers; erasure is unaffected. The warnings do reveal a currency and a date, and are withheld accordingly. Nothing found.                    |
| BS-007 | accessibility            | The notice uses a status region, native disclosure elements and text instead of colour, with component tests. It has not been used with a screen reader, and contrast in the dark theme is unverified.        |

| BS-009 | maintainability          | Two valuation paths live side by side until the flag is retired, inside a 2,500-line calculator; two stores hold the same data. Documentation exists (manifest, plan deviations, review summary).             |

## Rollback Plan

| Field                       | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Rollback trigger**        | Any of: users report wrong or missing values after enabling the flag; a sustained rise in "Exchange rate synchronization has failed" or "could not be read" log lines; recompute duration visibly worse; a bad stored rate that cannot be corrected quickly                                                                                                                                                                                                                                            |
| **Rollback steps**          | 1. Turn `isExperimentalFeatures` off for the affected users (or all users). The portfolio-changed event clears their snapshots and the legacy path runs on the next access. 2. If the problem is in the code, redeploy the previous release; the extra table is simply unused and the old code ignores the extra snapshot field. 3. Optionally drop the table (`DROP TABLE "ExchangeRate"`; it has no foreign keys) and mark the migration as rolled back with `prisma migrate resolve --rolled-back`. |
| **Estimated recovery time** | Flag off: a few minutes (debounce of 5 s plus the snapshot refresh of about a minute). Code rollback: one deployment.                                                                                                                                                                                                                                                                                                                                                                                  |
| **Rollback owner**          | The on-call or platform owner of the deployment; the client knowledge base does not name one                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Rollback risk**           | Users who had the flag on see their numbers change back to the existing behaviour, including its silent 1:1 fallback. Dropping the table discards the mirrored history, which a "gather max" rebuilds.                                                                                                                                                                                                                                                                                                 |
